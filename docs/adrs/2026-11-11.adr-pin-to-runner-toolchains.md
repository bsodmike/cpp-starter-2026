# Pin tool versions to what the CI runner images actually carry

- Status: accepted
- Date: 2026-11-11

## Context

The PRD recommends GCC 16.2 (August 2026) and Clang 23.1 (August 2026), with
floors of GCC 14 and Clang 21, and requires that the devcontainer and the CI
matrix read the same `.tool-versions` file.

Checking `actions/runner-images` on 2026-11-11 shows what the pinned runners
actually have:

| Runner | Compilers | CMake | Ninja |
| --- | --- | --- | --- |
| `ubuntu-26.04` | GCC 13.4 / 14.3 / 15.2, Clang 20.1 / 21.1 / 22.1 | 4.4.5 | 1.13.2 |
| `ubuntu-24.04` | GCC 12.4 / 13.3 / 14.2, Clang 16 / 17 / 18.1 | 3.31.6 | 1.13.2 |
| `windows-2025-vs2026` | Visual Studio Enterprise 2026 (18.11) | 4.4.5 | 1.13.2 |
| `macos-26` | Xcode 26.6 default, 26.4.1 available | - | - |

Neither GCC 16.2 nor Clang 23.1 is on a hosted image. Installing them per job
means a third-party apt repository (Clang) or building a compiler from source
(GCC 16 has no Ubuntu package), which costs CI time and adds an unpinnable
dependency on an external repository's current contents.

Two further findings from the same check:

- `windows-2025` historically provisioned Visual Studio **2022** (17.14, MSVC
  toolset 14.4x), which is below the project's MSVC 14.50 floor. The label now
  maps to the VS 2026 image, but the explicit `windows-2025-vs2026` label is
  what guarantees it.
- `ubuntu-latest` still resolves to 24.04, mid-migration to 26.04, which is
  precisely the drift the PRD warns about.

## Decision

Pin `.tool-versions` to the newest versions available on the pinned runner
images: CMake 4.4.5, Ninja 1.13.2, GCC 15.2.0, Clang 22.1.2. Keep the
CI-enforced floors where the PRD put them (GCC 14, Clang 21), so the pins sit
comfortably above the floor.

CI selects the compiler with `update-alternatives` against the preinstalled
packages instead of adding an apt repository. `libc++` and `mold` are not
preinstalled and are installed explicitly.

Use `windows-2025-vs2026` as the Windows runner label, not `windows-2025`.

The nightly pre-release job is the one place that uses `apt.llvm.org`, because
tracking compilers newer than the images carry is that job's entire purpose. It
is `continue-on-error`.

## Consequences

- CI installs no compiler from source and no third-party apt repository on the
  blocking path, which protects the under-15-minute budget and removes a
  supply-chain dependency from every PR.
- The project is not built with the PRD's recommended compilers on CI. The
  comment block at the top of `.tool-versions` records the gap and says to raise
  the two lines when the runner images carry them; the nightly job gives early
  warning of breakage before that happens.
- The devcontainer installs GCC and Clang from the Ubuntu 26.04 archive at the
  same pinned majors, so container and CI match. CMake and Ninja come from
  upstream GitHub release archives, since the distro versions lag the pins.
- Anyone wanting a newer compiler locally can use `dev-clang` with a sideloaded
  toolchain; the floor check and the presets do not care where the compiler came
  from. Clang 23.1.5 from an upstream LLVM release archive was used to verify
  this skeleton.
