# Two interface targets: public usage requirements vs build-only strictness

- Status: accepted
- Date: 2026-11-11

## Context

The PRD asks for one `INTERFACE` target carrying shared settings that every
target links, and separately for libraries to install a CMake package config so
consumers can `find_package(ACME)`. Those two requirements conflict when a
single target carries everything.

A static library links its `PRIVATE` dependencies into
`INTERFACE_LINK_LIBRARIES` as `$<LINK_ONLY:...>`, so an options target consumed
privately still has to be part of the export set. Export it, and consumers
inherit our warnings, sanitizer flags and coverage instrumentation. Nobody wants
`-Wold-style-cast -Werror` or `-fsanitize=address` arriving from a dependency.

## Decision

Split the settings across two interface targets:

- **`acme::options`** holds public usage requirements only: `cxx_std_23` and the
  standard-library hardening macros (`_GLIBCXX_ASSERTIONS`,
  `_LIBCPP_HARDENING_MODE`). These are ABI-relevant, so a consumer must compile
  with them. It is linked `PUBLIC` and is part of the export set.
- **`acme::build_options`** holds warnings, sanitizers, release hardening flags
  and coverage instrumentation. Targets link it as
  `PRIVATE $<BUILD_INTERFACE:acme::build_options>`. The generator expression
  resolves to nothing in the installed export, so the target never needs to be
  exported and its flags never reach a consumer.

## Consequences

- Within the build tree, everything still applies: tests linking `acme::core`
  are compiled and linked with the sanitizers, because `BUILD_INTERFACE` only
  strips from the install export.
- A package installed from a sanitizer or coverage build is **not**
  redistributable. Its objects reference `__asan_*` and `__ubsan_*` symbols that
  a consumer does not link, so the consumer's link fails with undefined
  references. This was caught by the consumer test in `tests/consumer/`, which
  is exactly why that test exists. `cmake/Install.cmake` now emits a warning at
  configure time when sanitizers or coverage are on, and CI tests install from
  the `release` preset.
- Adding a flag to the wrong target is the main hazard, so each target has a
  comment saying what belongs in it, and `CONTRIBUTING.md` explains the split.
- Deciding where a flag goes becomes a real question with a real answer: "would
  a consumer of the installed library be wrong without it?" If yes it is a
  usage requirement; if no it is build-only.
